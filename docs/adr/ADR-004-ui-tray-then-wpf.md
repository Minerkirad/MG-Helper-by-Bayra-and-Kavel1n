# ADR-004: сначала трей по IPC, WPF — после стабилизации ядра

**Статус:** РЕШЕНО на 3.0.0: UI = трей + меню, WPF отложен. Дата: 2026-11-27.

## Контекст

Пользовательский интерфейс сейчас — консольное меню [1..15] и трей-иконка. Меню
запускает PowerShell на каждый пункт (мигание консоли, зависимость от ExecutionPolicy),
трей показывает четыре состояния и баллуны, но не умеет показывать историю, профили
или дифф эталона. Полноценная WPF-оболочка (MVVM) — большой объём, и делать её до
того, как ядро и IPC стабильны, значит дважды переписывать биндинги.

## Решение для 3.0.0

WPF в 3.0.0 **не делаем**. Проверка критерия из раздела «Решение»: пользовательские
сценарии 3.0 закрываются треем (четыре состояния + SAFE MODE + баллуны по событиям)
и меню [1..15] (установка, новый эталон, диагностика, профили, восстановление MG).
История эталона с диффом и профили уже есть в меню; переносить их в отдельное окно —
объём, который не добавляет защиты и не проверяется parity-набором.

Что остаётся на будущее: WPF-оболочка поверх Named Pipe (IPC уже есть, контракт
статуса — `watcher.health.json`), когда появится сценарий, который трей и меню не
закрывают. Триггер пересмотра — такой сценарий в issue, а не «хочется красиво».

## Решение

1. Этап 5: трей переводится на IPC (статус, команды, события) — интерфейс остаётся
   прежним, но данные приходят без опроса файлов.
2. Этап 6: установщик и версии — без изменений UI.
3. Этап 7: решается, нужен ли WPF. Критерий «нужен»: пользовательские сценарии,
   которые нельзя сделать в трее (история эталона с диффом, профили, миграционный
   отчёт). Если такие сценарии закрываются меню и треем — WPF откладывается, 3.0
   выпускается без него.

## Последствия

- Риск «красивый UI поверх нестабильного ядра» снят: UI идёт последним.
- Меню остаётся точкой входа на всё время 3.0; его пункты не удаляются до появления
  равноценной замены.

## Откат

WPF-оболочка — отдельный exe; её отсутствие не влияет на watcher, трей и меню.
