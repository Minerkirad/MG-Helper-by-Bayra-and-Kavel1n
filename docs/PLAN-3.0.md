# MG Helper 3.0 — подробный план перехода

Документ раскладывает [ROADMAP-3.0](ROADMAP-3.0.md) (там — соответствие этапов A–E
исходному ревью 3.0 и оценки) в исполнимую последовательность работ: что делаем,
в каких файлах, чем доказываем, что не сломали, и когда можно удалять старый код.

**Правило документа:** этап закрыт только когда его DoD выполнен полностью.

> **Инцидент 2026-11-27.** Старый пакет 1.x перезаписал рабочую установку 2.6.1 на референсной машине (данные уцелели, 2.6.1 восстановлен из релизного ZIP). Поэтому установщик теперь отказывается затирать более новую установку без `-Force` (`Test-InstallDowngrade`), а бэкапы `backups\2.6.1` — обязательный шаг перед любым деплоем. Нельзя
переносить «зелёный» этап в «сделано», имея открытые пункты DoD.

---

## 1. Цель и критерии готовности 3.0

3.0 — это не «добавить функций», а **заменить компоненты без потери поведения**:
PS-watcher и C#-ядро сосуществуют, новое проверяется parity-набором на тех же
входах, старое выключается только когда новое доказало эквивалентность.

Готовность 3.0 (все пункты обязательны одновременно):

1. `MGHelper.Core` (C#) реализует **все** решения PS-watcher'а, и
   `tools\parity.ps1 -Implementation core` проходит `tools\parity\expected.json`
   без единого расхождения — на том же файле ожиданий, что и PS-реализация.
2. `tools\check.ps1` зелёный на чистом клоне (без живой установки) и **не содержит
   ни одного `[skip]`-блока**, который раньше не был бы зелёным.
3. Watcher работает как отдельный процесс с **Named Pipe IPC**; трей и меню
   говорят с ним по контракту, а не через «файл + опрос».
4. Данные и программа разложены по разным корням (`InstallRoot` / `DataRoot`),
   версии лежат в `Versions\<ver>\`, переключение — атомарной сменой указателя.
5. Установщик 3.0 ставит, обновляет и удаляет продукт с проверкой манифеста и
   хэшей, умеет откат на предыдущую версию без потери данных.
6. WPF-оболочка (или явное решение «остаёмся на трее») покрывает то же, что меню
   [1..15], и не требует PowerShell в UI-потоке.
7. Миграция 2.6.1 → 3.0 проходит на **резервной копии живой установки** (см.
   `backups\2.6.1\`), миграционный отчёт сохраняется, при ошибке — полный откат.
8. Старый PS-watcher удалён из деплоя, а `common.ps1` больше не содержит ветки,
   нужной только ему (или явно помечен как legacy-слой).

## 2. Незыблемые инварианты

Нарушение любого пункта — регресс, даже если тесты зелёные (эти инварианты и есть
то, что отличало v1 от 2.6.0):

1. При конфигурации по умолчанию эталон на диске не может измениться из-за записи
   чужого процесса — ни в окне охраны, ни после него; на выходе эталон возвращается.
2. `allowAdopt=true` включает adopt **только** для правки, сделанной после нашего
   apply в этой же сессии (время сравнивается в UTC; `appliedThisSession` обязателен).
3. Самоизлечение эталона берёт только `settings.golden.xml` / `.bak`; живые файлы —
   только по явному `-AllowLiveFallback`.
4. Охрана включена всю сессию (`guardWindowSec: 0`) и не выключается сменой PID.
5. Любой переход в «не защищаю» (mismatch, UnknownSession, неудачный apply) виден:
   событие в `events.jsonl` + жёлтый/красный статус в трее/UI.
6. Битый или чужой `state.json` не делает сессию «доверенной» (только SAFE MODE).
7. Деплой побайтовый: файлы пакета уходят в установку как есть (BOM, концы строк).
8. Любая деструктивная операция имеет точку восстановления (бэкап до записи,
   атомарная замена, откат при ошибке).

## 3. Отправная точка (2.6.1, факты)

- 85 проверок в `tools\check.ps1` (ALL GREEN под PowerShell 5.1), 21 сценарий parity.
- Контракты форматов: `docs\contracts\{state,health,events}.schema.json` +
  `tools\validate-contracts.ps1`.
- Защищённость подтверждена на живой установке: apply на запуске, откат чужой
  записи на 3-й и 20-й секунде сессии, эталон не тронут на выходе.
- Деплой: staged deploy 22 файлов в `%LOCALAPPDATA%\MG_Helper`, задача
  `MG_Helper_Watcher`, трей в Startup, `package_hashes.txt`.
- Резервная копия: `backups\2.6.1\` (исходники с тега + снимок живой папки), тег
  `v2.6.1`, релиз с ZIP и SHA256.
- Известные долги: `MGCore.cs` — beta-ядро без parity; IPC = файлы + событие
  `Local\MG_Helper_Stop` (на машине разработчика не открывалось — добавлен
  файловый фолбэк `stop.request`); версия одна, откат = переустановка.

## 4. Целевая архитектура

```
InstallRoot\                      (программа, read-only для пользователя)
  Versions\2.6.1\ ... 3.0.0\      неизменяемые каталоги версий
  current.json                    {"version":"3.0.0","path":"Versions\\3.0.0"} - переключается атомарно
  MGCore.exe  MGHelper.Watcher.exe  MGHelper.Tray.exe  (WPF)  MGHelper.UI.exe

DataRoot\                         (%LOCALAPPDATA%\MG_Helper — совместимость с 2.x)
  config.json  state.json  events.jsonl  watcher.health.json
  settings.golden.xml (+ history)  backups\  journal\  mg_snapshot\  vanilla_backup_archive\
  migration-report.json           результат миграции 2.6.1 -> 3.0

IPC: \\.\pipe\MG_Helper (ACL: только текущий пользователь)
  запросы: Status, Stop, ReloadConfig, ApplyGolden, RestartWatcher
  события: state-changed, event-line (тот же события-контракт, что events.jsonl)
```

Ключевые решения (оформить ADR в `docs\adr\`):

| # | Вопрос | Предложение по умолчанию | Как проверить |
|---|---|---|---|
| ADR-1 | Язык ядра | C# (net48) — один процесс с watcher'ом, PS остаётся только для меню/диагностики | parity + fault-injection |
| ADR-2 | Где живут данные | `DataRoot` = `%LOCALAPPDATA%\MG_Helper` (совместимость), `InstallRoot` = `%LOCALAPPDATA%\MG_Helper\App` | тест миграции на копии `backups\2.6.1` |
| ADR-3 | Формат IPC | Named Pipes + JSON-строки (тот же контракт, что события) | тест «два клиента, один watcher» |
| ADR-4 | UI | сначала трей по IPC, WPF — после стабилизации ядра | ручной приёмочный сценарий |
| ADR-5 | Судьба PS-watcher'а | остаётся на один релиз как `-Legacy`, затем удаляется | чек-лист §9 |

## 5. Этапы

### Этап 0. База (закрыт в 2.6.1)
Контракты, parity-раннер, сценарные блоки, fault-injection минимум, релиз и
резервные копии. DoD: 85/85, 21/21, `backups\2.6.1\` на месте.

### Этап 1. Testability: тестируемый watcher (S)

Цель — возможность прогонять **настоящий** цикл watcher'а в песочнице, не трогая
живую установку. Без этого нельзя ни event-level parity, ни fault-injection.

Задачи:
1. `MG3-021` Переопределяемый DataRoot: `$env:MG_HELPER_DIR` уважается и в
   `common.ps1`, и в `gta-settings-watcher.ps1` (по умолчанию — прежний путь).
2. `MG3-022` Интеграционный тест `tools\integration.ps1`: стартует watcher в
   песочнице, ждёт `watcher.ready` и `watcher.health.json`, посылает
   `stop.request`, проверяет `status=stopping` и события `watcher.start/ready/stop`.
3. `MG3-023` То же для «сессии» с фейковым процессом игры (как в ручном прогоне
   2.6.1): `session.start` → чужой записи нет → `session.end`.

DoD: `tools\check.ps1` вызывает интеграционный тест и остаётся зелёным; время
прогона < 40 с; живая установка не затрагивается (проверять по mtime файлов).

### Этап 2. Контракты+ и ADR (M)

1. `MG3-024` Схемы `profiles.json`, `journal_*.json`, `golden_key.json`,
   `config.json` (+ `cfgVersion`) в `docs\contracts\`.
2. `MG3-025` `schemaVersion`-миграции: таблица «версия → что поменялось → как
   читать», `Read-MgState` и `Get-ValidConfig` централизуют это.
3. `MG3-026` ADR-1..5 в `docs\adr\` (короткие, с последствиями и планом отката).
4. `MG3-027` Parity: добавить уровень **события** — сравнение последовательности
   `{event,data}` из интеграционного прогона.

DoD: все файлы состояния покрыты схемами; миграция схемы проверяется тестом
(старый формат → новый, и наоборот читается).

### Этап 3. Core из PS (M) — «эталон поведения»

1. `MG3-028` Вынести чистые решения в `MgHelper.Core.ps1` (PS-модуль
   `MgHelper.Core.ps1` + манифест): `Test-AdoptCandidate`, `Test-GuardActive`,
   `Test-SameSettings`, `Get-XmlSignature`, `Test-GoldenKeyMatchPure`,
   `ConvertTo-UtcTime`, `Read-MgState`, `Get-DefaultState`, policy-миграция.
2. `MG3-029` `common.ps1` подключает модуль (dot-source) и не дублирует тела
   функций; деплой-лист установщика и релизный ZIP включают `src\`.
3. `MG3-030` `tools\parity.ps1 -Implementation ps` работает **через модуль**, чтобы
   parity проверял именно тот слой, который потом заменит C#.

DoD: ни одна проверка `check.ps1` не меняет результат; parity 21/21; модуль
содержит 0 обращений к реестру/процессам (чистые функции — только входы/выходы).

### Этап 4. C#-ядро (L) — parity-gate

1. `MG3-031` `src\MGHelper.Core\` (C#, net48): те же решения, что в PS-модуле;
   входы/выходы — по схемам из `docs\contracts\`.
2. `MG3-032` `MGCore.exe` в режиме «решает, но не пишет» (`--dry-run`) и режим
   `--self-test`: читает `expected.json`, печатает фактические результаты.
3. `MG3-033` `tools\parity.ps1 -Implementation core` сравнивает вывод
   `MGCore.exe` с PS-модулем; расхождение — FAIL с diff'ом.
4. `MG3-034` `coreMode: "csharp"` в `config.json`: watcher делегирует решения ядру,
   но **запись** файлов остаётся в PS до этапа 5.

DoD: parity core = parity ps = expected.json (21/21 + event-level); `coreMode`
включается и выключается без перезапуска установки; откат — вернуть `coreMode`
в `powershell` (или удалить ключ).

### Этап 5. Watcher на C# + IPC (L)

1. `MG3-035` `MGHelper.Watcher.exe`: цикл, FSW, охрана, adopt, health, события —
   пишет в те же файлы под теми же схемами.
2. `MG3-036` Named Pipe `\\.\pipe\MG_Helper` + ACL текущего пользователя;
   команды `Status/Stop/ApplyGolden/ReloadConfig`; события в трей.
3. `MG3-037` Трей переводится на IPC (файлы остаются как резервный путь на один
   релиз); команды меню `[2]/[11]` используют pipe, а не `stop.request`.
4. `MG3-038` Fault-injection на живом watcher'е: kill посреди apply/adopt,
   read-only диск, повреждённый state.json, перезапуск игры внутри окна.

DoD: все сценарии §5 ROADMAP проходят на C#-watcher'е; PS-watcher можно запустить
рядом (но не одновременно) и получить те же события.

### Этап 6. InstallRoot/DataRoot, версии, установщик 3.0 (M/L)

1. `MG3-039` `Versions\<ver>\` + `current.json`, атомарное переключение; откат на
   предыдущую версию одной командой.
2. `MG3-040` Установщик 3.0: манифест с SHA256, проверка перед promotion, `.incomplete`
   для оборванных копий, uninstall по манифесту.
3. `MG3-041` Миграция 2.6.1 → 3.0: читает старую раскладку, пишет
   `migration-report.json`, при ошибке — откат и старое состояние нетронуто.

DoD: миграция на копии `backups\2.6.1\live-install-*.zip` проходит; после миграции
`check.ps1` и `parity.ps1` зелёные; повторная миграция идемпотентна.

### Этап 7. UI и релиз (M)

1. `MG3-042` WPF-оболочка (или решение «трей по IPC достаточно») — ADR-4.
2. `MG3-043` Пользовательские сценарии: установка, обновление, откат, диагностика,
   SAFE MODE — прогон по чек-листу вручную на чистой машине.
3. `MG3-044` Релиз 3.0.0: ZIP + SHA256, миграционная инструкция, CHANGELOG,
   тег, проверка RAW-файлов после пуша.

DoD: чек-лист §9 полностью; старый PS-watcher удалён из деплоя.

                                                        │

## 7. Гейты качества (на каждом этапе)

1. `tools\check.ps1` — ALL GREEN (без новых `[skip]`).
2. `tools\parity.ps1` — все сценарии expected.json, для обеих реализаций, у
   которых этап заявляет поддержку.
3. `/diagnose` на живой установке — «Всё в порядке» или честный список проблем.
4. Миграция и откат проверены на копии `backups\2.6.1\`, а не на живой папке.
5. Инварианты §2 не нарушены — отдельный прогон сценариев «чужая запись»,
   «битый state», «смена PID».
6. Ни одного файла пакета без BOM (PS 5.1) — проверка в `check.ps1` уже есть.

## 8. Риски и точки невозврата

| Риск | Признак | Ответ |
|---|---|---|
| Потеря истории эталона при миграции | после миграции `settings.golden.xml.old_*` меньше, чем было | миграция только копированием, оригинал не удаляется; откат из `backups\` |
| Двойная защита (PS + C#) одновременно | два процесса пишут `settings.xml` | mutex `Local\MG_Helper_Watcher` + проверка `coreMode`; в тестах — «второй экземпляр выходит» |
| Тихое расхождение решений | parity зелёный, а поведение другое | parity расширяется сценариями **из инцидентов**, а не только из кода |
| Пользователь на 2.6.1 не обновится | старая задача + новый установщик | установщик 3.0 сам останавливает старый watcher и мигрирует раскладку |
| Потеря трея при переходе на IPC | pipe недоступен на старых Windows/политиках | файловый путь остаётся резервным на один релиз (ADR-5) |

Точки невозврата: (а) удаление PS-watcher'а из деплоя — только после чек-листа §9;
(б) первая миграция схемы без обратного чтения — запрещена (ADR-2);
(в) смена `DataRoot` — только с миграцией и повторным запуском мастера.

## 9. Чек-лист «можно выключать PS-watcher»

- [ ] `parity.ps1 -Implementation core` = 21/21 + event-level сценарии.
- [ ] `check.ps1` ALL GREEN на чистом клоне без живой установки.
- [ ] Интеграционные тесты покрывают: apply на запуске, откат чужой записи (3 с и
      20 с), adopt по `allowAdopt`, SAFE MODE (mismatch и UnknownSession),
      битый state.json, остановку и перезапуск.
- [ ] Миграция 2.6.1 → 3.0 прошла на копии `backups\2.6.1\` дважды (идемпотентна).
- [ ] Откат на 2.6.1 проверен на копии: `install-gta-watcher.ps1` из
      `backups\2.6.1\source-v2.6.1.zip` возвращает рабочее состояние.
- [ ] Диагностика 3.0 объясняет состояние без чтения PS-логов.
- [ ] Релизные артефакты (ZIP, SHA256, тег, релиз) на месте, RAW-файлы проверены.

## 11. Что не входит в 3.0

- Новые функции для пользователя (кроме UI), переписывание профилей/истории эталона.
- Поддержка GTA V Enhanced сверх текущего определения варианта.
- Облачная синхронизация, автообновление по расписанию сверх текущего opt-in.
- Подпись кода (отдельный этап после 3.0; сейчас — SHA256 в релизе).
